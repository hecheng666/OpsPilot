# OpsPilot 项目讲解稿与追问 Q&A

> 所有数字来自 2026-11-25 本机实测：Ollama `qwen2.5:3b`，20 场景 × 3 基线，3 轮全量复跑 Top-1 均为 19/20。

## 一、3 分钟讲解稿

我做的是一个面向 Spring Boot 服务的 AI 故障排查 Agent，叫 OpsPilot。它解决的是值班场景里"告警响了，人要在一堆指标、日志、变更记录里翻半天"的问题。

整个项目分三块：一个可注入故障的订单 Demo 服务、一个 Agent 平台、一个 Vue 控制台。Demo 服务能注入慢 SQL、缓存击穿、线程池打满、下游超时四类故障，并暴露指标、结构化日志、变更事件和处置接口。平台侧每 5 秒采集一次，按阈值生成告警。

核心是自研的 Agent Runtime。我定义了统一的 Tool 接口，包含名称、描述、参数 Schema 和风险等级，一共 8 个工具：查指标、搜日志、看变更、查拓扑、检索 Runbook、读告警上下文、提议处置、执行处置。模型每轮必须输出一个 JSON，要么是"思考 + 调哪个工具 + 参数"，要么是"最终报告"，最多 6 步。每次工具调用都会落库并生成一条证据编号 E-xxxx，最终报告只允许引用本次真实产生的证据，模型编造的编号会被过滤掉，这样根因是可追溯的，不是一段无法验证的文字。

安全上做了分级：查询类工具是 READ，提议处置是 WRITE，真正执行是 CRITICAL。Agent 永远只能创建待审批动作，必须人工批准后才执行，执行写审计日志。评测里专门统计"未授权写次数"，结果是 0。

效果方面，我搭了 20 条场景、每条覆盖不同故障强度和形态，对比三个基线：纯阈值规则、只用 Runbook 检索加单轮模型、以及全工具 Agent。全工具 Top-1 命中 19/20，也就是 95%，Top-3 是 20/20；平均 5.7 步、7.6 秒；证据准确率和报告完整率都是 100%；未授权写 0 次。只做 RAG 的基线 Top-1 只有 45%，说明"检索到文档"不等于"能定位根因"，必须让模型主动去查指标和日志做交叉验证。

过程中最大的坑是小模型不稳定：3B 模型会重复调同一个工具、不收尾、输出非法 JSON。我的处理是协议层加 `format=json` 和输出长度限制，Runtime 层做重复调用拦截、同一工具最多两次、步数用完用独立的收尾提示词强制出报告，连续失败三次才降级到规则引擎。最终一轮 20 条场景 0 降级。

如果继续做，我会把它接到真实的 Prometheus 和 K8s 上，把评测集扩到线上真实故障，并加成本与延迟的联合优化。

## 二、高频追问 Q&A

### Q1：为什么自研 ReAct，而不用 LangChain 或模型原生 function calling？

A：两个原因。第一，这个项目的核心考点就是 Agent Runtime 本身，我需要能控制每一步的提示词、工具结果如何落证据、失败如何重试和降级，用框架反而把这些藏起来了。第二，本机跑的是 Ollama 上的 3B 小模型，function calling 支持不稳定，所以我用了更可控的自研 JSON 协议：模型每轮只输出一个 JSON 对象，我在服务端做解析、校验和纠正。代价是要自己处理非法输出，但这正好是我想讲的部分。

### Q2：规则基线 Top-1 是 100%，比 Agent 还高，那为什么还要用大模型？

A：这个规则基线是照着这 20 条场景的故障特征手工调过阈值的，属于"对着考题调参"，命中率高是必然的，但它只会输出一个故障标签，没有证据链、没有备选根因、没有影响面、没有处置建议和预防措施，也没法处理没见过的组合故障。Agent 是 95%，差距在一条边界样本上，但它给出的是可追溯的完整报告，并且能跨指标、日志、变更、拓扑做交叉验证。我在 README 里也明确写了这一点，不把规则基线当成"被击败的对手"来吹。

### Q3：19/20 里没命中的是哪条？为什么？

A：3 轮复跑里每次未命中的场景不完全一样，分别出现过：下游级联故障被判成慢 SQL、轻度过载、缓存回源被判成下游问题。共同点是这些场景的信号本身就重叠——比如下游超时会同时抬高本服务的响应时间和错误率，缓存回源会抬高 DB RT。3B 模型在边界样本上会出现判因抖动。我的定位是：主链路稳定在 95%，剩下 5% 需要更大模型或更多判别特征，而不是靠调提示词硬凑到 100%。

### Q4：怎么保证模型不编造证据？

A：证据不是模型生成的，是工具执行时由 Runtime 生成的。每次工具调用成功，`EvidenceService` 落一条 `evidence` 记录并分配 E-xxxx 编号。最终报告生成后，我会把 `evidence_ids` 和本次运行真实产生的编号集合做交集过滤，不存在的编号直接丢弃；同时收尾提示词里会显式列出本次可用编号。所以报告里的每个证据编号都能在数据库里回查到原始工具结果。

### Q5：危险动作怎么防？

A：三层。第一层是工具风险分级，`execute_remediation` 是 CRITICAL，`propose_remediation` 是 WRITE，其余是 READ。第二层是状态机：Agent 只能创建 `PENDING_APPROVAL` 的动作，`execute_remediation` 只接受 `APPROVED` 状态，Agent 没有审批入口。第三层是审计：谁批的、什么时候批、参数是什么、执行结果如何，全部写 `audit_log`。这里踩过一个真实的坑：最初执行工具写审计时把 `actor` 硬编码成 `agent`，人工审批后的执行也被记成 Agent，评测页因此误报 12 次"未授权写"。修复是把操作者从审批链路透传进 `ToolContext`（人工执行记审批人，Agent 自主调用记 agent），并回刷历史记录；修复后 `actor='agent'` 且 `action='EXECUTE_REMEDIATION'` 的记录为 0，未授权写只统计"绕过审批的执行"。

### Q6：3B 模型不稳定，具体怎么解决的？

A：分四层。协议层：请求带 `format=json`，限制 `num_ctx=8192`、`num_predict=512`，避免无限生成触发 Ollama 的重复 token 中断。调用层：单次失败自动重试，连续 3 次失败才判定模型不可用并降级到规则引擎。循环层：记录每个工具的调用次数和参数指纹，同一工具最多 2 次，重复参数立即终止循环，防止模型原地打转。收尾层：步数用完后换一套独立的 FINAL_PROMPT，只允许输出最终 JSON，并附上本次可用证据编号；再失败两次才走规则兜底。最终一轮 20 条 0 降级。

### Q7：为什么最多 6 步？步数不够怎么办？

A：6 步是基于工具面的取舍：指标、日志、变更/拓扑、Runbook 各一步，加一次补充验证和最终报告，刚好覆盖典型排查路径。步数用完后不是直接失败，而是进入强制收尾：用已有证据生成报告，并在提示词里要求根因至少引用一条真实证据。如果模型仍然不配合，才降级到规则报告。这样保证任何情况下都有结构化输出，不会挂死。

### Q8：评测怎么保证公平和可复现？

A：每条场景都走同一套流程：先恢复所有故障，再注入当前场景，等两个采集窗口让指标稳定，然后跑基线，评分，最后恢复。查询窗口从注入时刻开始算，避免上一条场景的残留指标污染下一条。三条基线用同一批场景、同一套评分逻辑：期望根因是关键词数组，命中第 1 个算 Top-1，命中第 2 到第 3 个算 Top-3，未命中记 0。评测结果、逐场景明细都能在控制台回看和导出 JSON。

### Q9：Runbook 检索具体怎么做的？为什么用 RRF？

A：10 篇中文运维手册按 300-500 字切块，用 `bge-m3` 生成向量存库。检索时两路召回：一路是关键词评分，中文用 CJK bigram、英文用分词；另一路是向量余弦，相似度低于 0.3 的丢弃。两路结果用 RRF、k=60 融合，避免某一路的分数尺度压倒另一路。RRF 的好处是不需要调权重，对异构分数量纲更稳。

### Q10：SSE 是怎么实现的？断线怎么办？

A：Agent 排查接口是 `text/event-stream`，Runtime 每产生一个步骤就推一个 `step` 事件，报告生成后推 `report`，最后推 `done` 并带 `runId`。前端用 `EventSource` 接收，同时把每一步落库，所以即使流断了，也能用 `runId` 从 `agent_step` 和 `evidence` 表把时间线完整回放出来。控制台还支持 `/agent?runId=xxx` 深链直接打开某次运行。

### Q11：如果上生产，还缺什么？

A：四块。可观测性要接 Prometheus、ELK、真实链路追踪，替换现在的模拟采集；执行面要接 K8s 和发布系统，把"模拟生效"换成真实变更，并加灰度、回滚和熔断；权限要接企业 SSO 和审批流，按服务、环境、动作类型做细粒度授权；评测要扩到线上真实故障回放，并加成本、延迟、误报率的联合指标。这些我在 README 的"已知限制"里都写明了，不假装已经是生产系统。

### Q12：这个项目你个人做了什么？最难的点是什么？

A：从需求、设计到实现和评测都是我一个人做的。最难的不是把 Agent 跑通，而是让它在小模型上稳定、可评测、可解释：要设计一套模型能稳定遵守的 JSON 协议，要处理重复调用和不收尾，要把每次工具结果变成可回查的证据，还要让三条基线在同一套流程下公平对比。这些工程约束比单次演示更能体现 Agent 落地能力。还有一个印象很深的点：评测指标反过来帮我发现了实现缺陷——人工审批后的执行被误记为 Agent 执行，"未授权写"从 0 变成 12。顺着指标查到 `actor` 被硬编码，改成从审批链路透传并回刷历史记录后才归零。这让我更相信"可评测"不是附加项，而是能暴露实现问题的调试工具。
